02 / Field solution architecture

Discover → Frame → Require → Architect

The full loop does not stop at a working build; it reaches safe adoption and operation.

DiscoverFrameRequireArchitectProveCommunicateAdoptOperateLearn

Every substantial customer problem must also pass through:

Discover → Frame → Require → Architect → Prove → Communicate → Adopt → Operate → Learn

Discover

Learn how work is actually performed. Ask before assuming.

Frame

State the customer problem, desired outcome, constraints, risks, non-goals, and unknowns.

Require

Convert stakeholder concerns into functional, non-functional, control, evidence, security, operational, and economic requirements.

Architect

Design the smallest credible system that satisfies the important requirements.

Prove

Use a PoC to test the riskiest assumptions, not to build a miniature production system.

Communicate

Explain the same architecture appropriately to engineers, operations, risk, security, executives, and commercial stakeholders.

Adopt

Define how the solution moves from demo to controlled production use.

Operate

Define ownership, monitoring, escalation, incident response, reconciliation, and change control.

Learn

Use production evidence, failures, objections, and changing requirements to revise the system.

03 / Scalable verification

Specify before you check

What must never happen, what must eventually happen, and under which assumptions?

State the property

What must never happen?

What must eventually happen?

Under which assumptions?

Choose the simplest useful verification method. Run it, inspect the result, and state what was not proved.

Verification ladder, not a ranking
Unit / example testsHypothesis property testingHypothesis stateful testingTLA+ / TLCLean

Later methods are not automatically better. A passing check is evidence only for its stated claim and assumptions.

As responsibility grows, human attention does not scale at the same rate as code volume.

For every consequential workflow, the learner must be able to ask:

1. What must never happen?

2. What must eventually happen, and under which assumptions?

3. What happens under retries?

4. What happens under timeouts?

5. What happens under crashes?

6. What happens when requests overlap or operations run concurrently?

7. Who owns each requirement?

8. What check can run without the architect personally inspecting every execution?

The learner must choose the simplest useful verification technique rather than reaching automatically for the most sophisticated tool.

Verification ladder:

  • Unit/example tests — known cases and specific sequences.
  • Hypothesis property-based testing — generate inputs to search for edge cases.
  • Hypothesis stateful testing — generate action sequences to search for failures across state transitions, retries, and interacting operations.
  • TLA+ with TLC — model system behavior and explore a chosen finite model, especially where retries, crashes, concurrency, and interleavings interact.
  • Lean — check a proof of a precise claim under explicit assumptions when a critical algorithm or invariant is worth proving.

Mandatory interpretation rules:

  • Passing property/stateful tests is evidence, not mathematical proof.
  • A TLA+ model is an abstraction; the implementation must still be checked against the model.
  • A Lean proof proves the formalized claim under its assumptions; the learner must check that the claim actually matches the shipped system.
  • A proved safety rule can still describe the wrong product.
  • Safety properties must be considered alongside useful progress/liveness. For example, “never perform the same payment twice” is insufficient if the system can satisfy it by rejecting every payment.
  • Verification output never substitutes for understanding what the property means institutionally.

For formal verification work, the evidence package must state:

  • workflow checked
  • safety property / “must never” claim
  • liveness or progress property / “must eventually” claim where applicable
  • assumptions
  • chosen verification technique and why
  • results
  • limitations
  • what could not be run, explored, or proved
  • relationship between the checked model/claim and the implementation.

AI may help with formal verification after the learner has first stated, in their own words:

  • the workflow
  • what must never happen
  • what must eventually happen
  • the assumptions being made.

AI may then:

  • suggest the simplest useful check
  • help generate candidate property/stateful tests
  • help translate learner-authored properties into candidate TLA+ / TLC or Lean scaffolding
  • help run or interpret tool output
  • propose adversarial sequences.

AI-generated verification material is not evidence of learner capability until the learner can:

  • explain the property
  • explain the assumptions
  • run the check
  • interpret the result
  • modify the property or scenario
  • state what the check did not establish.

The agent can write checks. The learner remains responsible for understanding what those checks mean.

06 / Dedicated architecture

Agent memory & state

Twelve dimensions keep remembered information from becoming unexamined authority.

Memory is not merely “more context.” It changes future agent behavior and therefore changes the risk surface.

01

TYPE — Is the information transient context, session state, durable workflow state, episodic memory, semantic memory, procedural/configuration memory, or an external source of truth?

02

WRITE AUTHORITY — Who or what may create, update, summarize, overwrite, invalidate, or delete it?

03

READ / RETRIEVAL AUTHORITY — Which principal, task, tenant, workflow, or agent may retrieve it?

04

PROVENANCE — Where did the remembered item come from, when was it created, and what transformed it?

05

FRESHNESS — When does it become stale, expire, or require revalidation?

06

CONFLICT — What happens when remembered items disagree with each other or with the current source of truth?

07

TRUST — Is retrieved memory evidence, untrusted context, a hint, or authoritative institutional state?

08

ISOLATION — Can memory cross user, customer, tenant, case, or workflow boundaries?

09

POISONING — Can hostile or incorrect content be written and later influence action?

10

RETENTION — What must be retained, summarized, archived, or deleted, and who owns that decision?

11

AUTHORITY — Can remembered content change effective authority? The default answer must be no unless an explicit current authority source says otherwise.

12

RECOVERY — What happens to memory/state after crash, rollback, model change, policy change, or incident?

Remembered information may influence reasoning, but memory must not silently manufacture authority or become evidence merely because the agent retained it.
07 / Operational accountability

The integrated system under control

Twelve questions expose coupling, emergence, evidence, audit, deviation, restoration and change.

01

AGENT — What are the capabilities and failure modes of the agent system before institutional integration?

02

INSTITUTION — What identities, systems, data, workflows, policies, humans, and decision rights already exist?

03

COUPLING — Through exactly which interfaces, credentials, APIs, tools, queues, memory stores, and human approvals are the two systems connected?

04

EMERGENCE — What new powers and failure modes appear only because of that coupling?

05

BLACK-BOX ASSUMPTIONS — Which claims about a vendor component are documented, experimentally observed, inferred, or unknown?

06

EVIDENCE — Which consequential actions generate structural evidence automatically at execution time?

07

AUDIT — Which evidence is reviewed periodically, and which events trigger immediate review?

08

DEVIATION — What constitutes material deviation and what deterministic response follows?

09

AUTHORITY CONTRACTION — When does autonomy narrow, human approval become mandatory, or the agent become quarantined?

10

RESTORATION — Who may restore authority, on what evidence, and under which version/configuration?

11

CHANGE — Which model/runtime/tool/configuration changes require re-characterization or re-approval?

12

HANDOFF — Can operations, security, risk, and engineering run and inspect the integrated system without depending on the original architect?

Audit awareness may influence agent behavior; auditability must not depend on agent cooperation.
Normal compliant operation preserves bounded autonomy. Material deviation triggers containment, evidence capture, authority contraction, and review. Authority restoration is explicit.
Model-dependent behavior may change. System-enforced authority invariants must not silently change with the model.

01 / Proof

PoC doctrine

A PoC resolves a decision-producing uncertainty, not a miniature production build.

What uncertain assumption could make this entire architecture or commercial proposition fail?
HypothesisCustomer value affectedUncertaintyExperimentSuccess criterionFailure criterionEvidence collectedDecision after result

A PoC is not a miniature production system.

A PoC exists to answer:

What uncertain assumption could make this entire architecture or commercial proposition fail?

Every PoC must state:

  • hypothesis
  • customer value affected
  • uncertainty
  • experiment
  • success criterion
  • failure criterion
  • evidence collected
  • decision after result

A visually impressive demo without a decision-producing hypothesis does not satisfy the PoC requirement.

Formal methods are used to reduce design uncertainty, not to create an aura of mathematical certainty.

For a workflow, begin with meaning:

What must never happen?
What must eventually happen?
Under which assumptions?

Then consider retries, timeouts, crashes, and overlapping requests.

Then choose the simplest useful check.

The learner must be able to explain why a particular job calls for:

  • an example/unit test
  • Hypothesis property-based testing
  • Hypothesis stateful testing
  • TLA+ with TLC
  • or a Lean proof.

No tool is mandatory merely because it is sophisticated.

A passing check is not equivalent to “the system is correct.”

A proof of the wrong property can still produce the wrong product.

Why v0.6 exists and how it changed

1. Why v0.6 exists

Curriculum v0.3 was built on the technically credible Enterprise AI control-layer foundation of v0.2 and added the Field Solution Architecture layer required for Vendor-Side Role B.

That technical/control and field-architecture objective remains correct.

The target role remains:

Vendor-Side Role B — a customer-facing technical architect who can enter an unfamiliar regulated enterprise, discover the real problem, translate institutional/business/regulatory constraints into a technical architecture, prove the risky assumptions through a PoC, communicate the design to different stakeholders, and help move the system toward safe adoption.

v0.3 corrected the earlier gap between:

build → test → defend

and the fuller field requirement:

discover → frame → require → architect → prove → communicate → adopt → operate → learn

v0.4 adds one further correction.

AI-assisted software creation can increase the amount of code and system behavior under one person’s responsibility faster than human attention can scale. Reading every generated line is therefore not a sufficient assurance strategy for consequential systems.

The learner must progressively move from only inspecting implementation toward specifying and checking:

  • clear requirements
  • ownership
  • system properties
  • assumptions
  • automated checks that can run without continuous personal inspection.

This does not replace coding. The learner continues to write, read, debug, and own code. The new requirement is to add scalable reasoning above the code.

The curriculum therefore adds a bounded formal-verification layer:

state the property → state the assumptions → choose the simplest useful check → run it → inspect the result → state what was not proved

This is not a formal-methods specialization and does not add a new curriculum stage.

v0.5 adds one further bounded correction.

A control-layer architect cannot decide what an AI agent should be allowed to do without first understanding what kind of system the agent actually is: what it can perceive, infer, plan, remember, invoke, retry, misunderstand, and do once tools and authority are attached.

v0.4 already covered many of these concerns across identity, state, reliability, security, authority, evaluation and inference economics, but did not require the learner to integrate them into one explicit agent capability-and-failure model before designing controls.

The learner must therefore build and defend an explicit model of:

  • model vs agent vs orchestrator/runtime vs tool boundaries
  • inputs / context / retrieval available to the agent
  • planning / reasoning behavior and uncertainty
  • tool selection and consequential action surfaces
  • memory / durable state / stale-context risk
  • autonomy and escalation boundaries
  • nondeterminism and long-horizon drift
  • hallucination / unsupported inference
  • retries, timeouts, crashes and overlapping actions
  • prompt injection / tool misuse / data-boundary failure
  • observability and what can be reconstructed after action
  • capability limits and when specialist escalation is required.

The purpose is not to create a separate “agent science” specialization.

The purpose is to make the permanent design sequence explicit:

capability model → failure model → authority model → control architecture → evidence

v0.6 adds one further bounded correction.

v0.5 made the agent itself an explicit object of study. That is necessary but incomplete for Vendor-Side Role B.

There are two distinct systems that must be understood.

SYSTEM A — THE AGENT SYSTEM

The agent system includes, depending on implementation:

  • model
  • system/developer instructions
  • orchestration/runtime
  • context
  • retrieval
  • memory/state
  • tools
  • planning/reasoning loop
  • retry/cancellation behavior
  • model/runtime configuration.

Question:

What kind of system is this agent, what can it do, and how can it fail?

SYSTEM B — THE INTEGRATED AGENT–INSTITUTION SYSTEM

A second system comes into existence when the agent is connected to an institution through:

  • enterprise identity and credentials
  • permissions and delegated authority
  • data and records
  • APIs and tools
  • workflows and queues
  • humans and approvals
  • policy and risk controls
  • operational infrastructure
  • monitoring and incident response
  • vendor/runtime dependencies.

Question:

What new power, behavior, and failure modes emerge because these systems are now coupled?

The integrated system can exhibit consequential behavior that neither the agent nor the institution possessed independently.

Therefore the curriculum must explicitly teach:

  • agent memory/state architecture rather than treating memory as one failure bullet
  • installation and integration of an unfamiliar black-box/vendor component from its exposed contract and documentation
  • experimental characterization when internals are unknown
  • modelling of emergent behavior created by agent–institution coupling
  • continuous structural evidence capture rather than relying on the agent to remember to create evidence
  • periodic and event-triggered audit over that evidence
  • deterministic authority contraction, containment, or quarantine after material deviation
  • explicit authority restoration after review
  • reassessment when a model/runtime version changes, because model-dependent behavior can change while institutional authority invariants must remain structurally enforced.

The permanent design sequence therefore becomes:

agent nature → capability/failure model → memory/state model → black-box integration → agent–institution integration model → authority → controls → continuous evidence → operational feedback → safe adaptation

This remains a bounded Role-B correction.

It does not add a new curriculum stage, require a particular agent framework, or turn the learner into a model researcher, platform SRE, or vendor-product specialist.
